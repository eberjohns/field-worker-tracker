## Critical: wrong results or broken in production

### C1. OT2 rule in code contradicts the confirmed rule
`modules/attendance/service.py:281` hard-codes `is_ot2_weekday = weekday_name == "SUNDAY"`, and `rules/attendance/engine.py:223-230` uses it:
- **Every Sunday is OT2 for everyone**, even when the worker's weekly off day is another day.
- **Work on the worker's own weekly off day goes to OT1** (`day_type = "WEEKLY_OFF"`).

Confirmed rule (DEC-01, owner 19 Nov): OT2 = public holidays + the worker's own weekly off day, **nothing else**. Batch 4 updated the register but not the code. Line 279 also defaults a missing `weekly_off_day` to `"SUNDAY"` silently.

### C2. The background worker does nothing, so scheduled checks never run
`backend/src/fw/worker.py` only logs `worker_started` and waits ("In future phases, Procrastinate worker runs here"). Nothing schedules:
| Function | Called from | Effect |
|---|---|---|
| `AttendanceWatchdogs.check_no_activity` | nowhere | NO_ACTIVITY alerts never raised |
| `AttendanceWatchdogs.check_stale_devices` | nowhere | STALE_DEVICE alerts never raised |
| `PendingVisitsService.check_pending_visit_reminders` | nowhere | pending-visit reminders never sent |
| `PendingVisitsService.detect_pending_visits` | manual API call only | pending visits appear only if someone presses the button |
| `NotificationService.check_document_expiry_alerts` | lazily, when someone opens the alerts list (per-process global flag, errors swallowed) | no expiry alert unless a user opens the alerts list that day |
| `ArchiveService.run_retention_purge` / yearly archive | manual admin endpoint | retention (DEC-38) never runs on its own |

### C3. Live map and alerts break with several server processes
Production runs `uvicorn --workers 4` with `replicas: 2` (8 processes). These are in-process memory only:
- `StreamTicketManager._tickets` (`events/live_publisher.py:20`): the ticket from `/live/stream-ticket` is stored in one process, so `/live/stream` fails with `INVALID_TICKET` when it lands on any of the other 7 (about 7 times in 8).
- `LivePositionBroadcaster._subscribers`: a position update only reaches browsers connected to the same process that received the event. `enrichment.py:296` sends `NOTIFY live_positions` but **nothing runs `LISTEN`**, so other processes never hear it.
- `_last_doc_expiry_scan_date` (`notifications/service.py:17`) is per process.

### C4. The push provider pretends to send
`adapters/push/provider.py` `FcmPushProvider.send_silent` logs `fcm_push_dispatched` and returns `True` without calling FCM. Silent "sync now" pushes (`sync/service.py:1086`) never reach phones, but the logs say they did.

## High

### H1. Server date used instead of the site's local date (golden rule 6)
There are 30 `date.today()` calls (10 in `scheduling/service.py`, 5 in `api/employees.py`, 4 in `api/jobs.py`, 3 in imports, plus reports and payroll). Containers run on UTC, so between 00:00 and 04:00 Dubai time "today" is still the previous day. Examples:
- `scheduling/service.py:3355` feeds `today_work_date` to the reassignment notice rule, so at 01:00 Dubai a **same-day reassignment passes the "one day in advance" rule**.
- Crew-break effective date (`api/employees.py`, imports), import default effective dates, staffing-gaps and roster reports.

`Asia/Dubai` is also hard-coded in `api/live.py` (×3), `api/dashboard.py` and `api/pending_visits.py`, and `events/service.py:44` maps the country to a time zone in code. KSA sites would get the wrong day. There should be one helper, e.g. `site_today(country)`.

### H2. Swallowed exceptions around database queries in attendance
`attendance/service.py:97` (payroll-lock check) and `:122` (salary standard hours and break) use `except Exception: pass`. If either query fails:
- the lock check fails open, so finalized days can be recalculated;
- the salary load falls back to 8 h and no salary break without any flag;
- in PostgreSQL the failed statement aborts the transaction, so the next query fails with "current transaction is aborted", far from the real cause.

The other swallowed exceptions (`scheduling/service.py:281`, `reports/service.py:424`, `events/enrichment.py:296`) are lower risk but should at least log.

### H3. Month-end report generation can break payroll approval
`reports/listeners.py` runs `generate_month_end_reports` inside the payroll transaction and catches every exception. A failure part-way through leaves the PostgreSQL transaction aborted, so the payroll approval commit fails with a misleading error. Or, if nothing was flushed yet, the reports are silently missing. It should run after commit (post-commit handler or worker job), and failures should raise an alert.

### H4. Rate limiting and login lockout are promised but missing
The mobile contract (§ auth, error table) promises "Login locks after repeated failures" and `429 RATE_LIMITED` with `Retry-After`. No code produces `RATE_LIMITED`, and there's no lockout or failed-attempt counter for the web or mobile login.

### H5. Broken web call: the worksite budget's revision list is always empty
`web/src/routes/WorksiteDetail.tsx:288` fetches `/api/v1/payroll/salary-revisions`, but the route is `/api/v1/salary-revisions`. The 404 is swallowed (`.catch(() => {})`), so the salary-revision dropdown for the job budget is always empty.
